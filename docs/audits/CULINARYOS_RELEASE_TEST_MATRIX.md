# CulinaryOS release test matrix — ShorelineOps

Baseline date: 2026-09-20. This is a proposed release verification plan and a record of checks actually reported by the audit runner. No release candidate or production environment has been designated; this document is not a release gate approval.

**Status vocabulary:** PASS means the recorded command passed in the stated environment. NOT RUN means no runtime evidence was collected for this scenario. SOURCE FAILURE means source inspection establishes a defective implementation, while the end-to-end reproduction remains NOT RUN. IMPLEMENTATION GAP means the inspected application lacks the required flow; an explicit approved launch exclusion can make a scenario N/A. Existing unit/system coverage is not a substitute for a passing browser or production test.

**Baseline environment:** Windows, Node v24.21.0, compared with the project's declared Node 20 baseline. The system suite used isolated disposable SQLite and reported 228 passed, 0 failed. PostgreSQL behavior was not exercised. Production, live payments, actual resident data, vendor accounts, email and physical hardware were not used. Use synthetic fixtures and isolated environments for every destructive test below. Record commit, fixture, browser/device, operator, log and observed outcome when executing a case. Never include tokens, passwords, PHI or payment details in artifacts.

Evidence appendices: [security/data](SECURITY_DATA_EVIDENCE.md), [product/UX](PRODUCT_UX_EVIDENCE.md). Command logs are linked in baseline rows. ## Execution order and evidence closure

1. Preserve baseline logs and finalize dependency reachability triage; reproduce on the intended runtime and PostgreSQL if supported for launch. Configured lint/type compilation passed; it is not a separate style/lint rule suite.
2. After approved implementation, test production seed separation, MFA purpose enforcement, resident admission/NPO normalization, scanner failure handling, save truth and real admin persistence. These precede any real resident pilot.
3. Complete single-facility core E2E, browser/mobile/accessibility checks and an isolated backup/restore drill. Shared tenancy, automated billing and live integrations remain excluded unless their conditional P0 tests pass.
4. Review marketing/legal claims and support route; run staging production-equivalent smoke and observability exercises.
5. Only after a release candidate and environment are designated, summarize current case outcomes in a separate release gate report. A build or 228 passing existing tests cannot close NOT RUN rows automatically.

For each execution, append a dated evidence entry identifying case ID, commit, sanitized fixture/version, environment/runtime/database/browser, exact steps, actual result, artifact link and reviewer. Retain failed runs and reruns; do not overwrite failures with unqualified PASS. Mark a case N/A only with the founder-approved scope exclusion, rationale and corresponding product/marketing restriction.
