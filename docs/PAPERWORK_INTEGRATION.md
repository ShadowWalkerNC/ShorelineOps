# ShorelineOps companion integration

PR-01: Production & Service gains a Paperwork tab; weekly2/daily3, optional daily extras, explicit complete44 and one-page blank prep/service forms. Browser Print / Save as PDF uses deterministic Letter HTML generated from the standalone plugin's same templates.

PR-02: a .srmenu transfer contains canonical transcription and hash-verified original JPEG/PNG/PDF bytes. It carries no usable approval across applications. Privacy review of source, filename and transcription is mandatory before intake. User reviews the original in the plugin, then confirms all42 in ShorelineOps; production rendering binds to the exact current content hash and rejects unresolved fields. Imports are stateless, not written to resident/menu databases. Any correction/replacement requires plugin re-review and a new transfer. Area must exactly match; shared menus are not inferred.

PR-03: same-origin authenticated /api/paperwork endpoints use existing production.read/write capabilities. No permission allowlists, clinical routes, resident projections, census math, DB schema, clinical substitutions or NPO/allergen gates changed. No source filepath input or filesystem read from caller data. No image OCR/AI provider, source content logging, temporary upload files or new runtime dependency. Browser file is limited to900KB because the service's existing1MB JSON limit is retained. Source evidence is included and hashed but privacy remains a human/host attestation, not automatic image detection.

Backend ownership: server/vendor/ross-paperwork/engine.cjs is generated by packages/shorelineops-plugin/scripts/build-shoreline.mjs. Its manifest pins version and SHA256; do not hand-edit the bundle. Rebuild from maintained standalone source when templates change. The runtime vendor contains no menu/photo fixture. Historical source fixtures live only in the source plugin package and remain unapproved. server/src/paperwork.ts loads the vendor package; server/src/routes/paperwork.ts validates and renders; frontend keeps transfer/current review only in mounted component state. Refresh loses the imported state and approval by design.

Flow: plugin source review -> menu_export -> .srmenu file -> ShorelineOps privacy confirmation -> inspect -> optional preview -> explicit42-choice confirmation -> deterministic render -> browser print/savePDF. Blank forms skip menu intake. Backend approval is per render and not a durable signoff.

Drafts can be printed for layout review before food approval, matching the plugin's existing demo workflow. They always retain the review watermark and are labeled Print draft / not for production in the UI. Production pages require the exact-revision gate. Import never changes the selected resident area silently. Mobile preview scales on screen only; Letter print dimensions and typography remain unchanged.

Limits: no raw photo extraction inside ShorelineOps, no server-generated downloadable PDF or hosted ChatGPT bridge. Device print, physical print and live hosting require their own acceptance checks. The integration can be tested locally without touching a real resident record. Deployment is separate; no push or production deployment is implied. Remove the Paperwork tab/route/vendorCOPY to roll back; no database migration exists.

## Reviewed counts extension (engine0.11)

PR-04: optional version2 .srmenu includes one confirmed plugin scan, its hash-verified redacted source and retained extracted evidence. Existing version1 files remain supported. Source menu and native area binding is validated; unknown/missing/ambiguous/inconsistent counts are refused. ShorelineOps shows source and compact per-meal counts, then requires a separate exact-count-hash confirmation on every final render. Replacing imports, changing area or revoking privacy clears confirmations/preview. Day coverage is enforced. Explicit0 is preserved; absent optional staff/extras remain blank. Anonymous selection sheets aggregate only within their own batch. Counts fill SR03 and cook A/B headers, not item quantities, prep rules or SR02.

The UI warns that imports are offline snapshots: plugin changes cannot invalidate already-downloaded files or mounted Shoreline state. After menu/count changes re-export and re-import before re-confirming. No autosync/background alerts claimed. Source privacy is attested by the user, not automatic detection. Existing capabilities/body limit/stateless storage/no resident DB remain. Optional count sources are shown as image or PDF download. Browser acceptance harness supports PAPERWORK_BROWSER_PATH for an installed browser; current local390/1280 run used Edge because bundled Playwright browser was unavailable. Real phone/physical print and real tally handwriting acceptance remain separate.

Full plugin source is now packages/shorelineops-plugin with its own lock/dependencies, rootbuild/test/release commands and scopedCI. The existing external Plugins/sylvia-menu checkout is historical, not the maintained owner. Original S-wave PNG shared byte-for-byte across app/plugin/client packages. PublisherCulinaryOS, free, all supported countries. Plain-language onboarding, three-step app paperwork view, dedicated import-folder configuration for localMCP clients.

Native adapter obtains name/wings from the initialized facility_config record already written by app setup. No fallback to a fixedRoss roster. Wing IDs use stable normalized names; duplicate/invalid IDs or missing/uninitialized setup fail closed. Query uses this single-facility deployment’s existing default setup record; no tenant switching or DB mutation/schema added. Test routers inject known profiles. UI selects an available service area but never silently switches to an imported menu’s area. Metadata/food/count confirmation remains per-render/current-hash.

Multi-platform artifacts are prepared, not automatically published. See docs/PLUGIN_DISTRIBUTION.md for public-submission gaps. Root npm run paperwork:vendor rebuilds the pinned app engine from repo source. Do not manually edit server/vendor/ross-paperwork/engine.cjs. Source packages include permanent test fixtures; runtime app/vendor remains menu-free.
